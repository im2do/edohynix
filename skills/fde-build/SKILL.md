# 끝까지 이어지는 작은 기능 만들기

응답과 새로 작성하는 사용자 화면 문구는 기본 한국어로 쓴다. 원문 인용·고유명사·코드 식별자는 보존한다. 뜻이 같은 한자나 일본어 단어를 한국어 설명에 섞지 않는다. 사용자가 다른 언어를 요청하면 그 요청을 따른다.

FDE_HARNESS.json이 있으면 실제 package·progress·state 경로를 확인한다. 없으면 현재 키트의 scripts와 과제 폴더의 기존 기록을 사용한다. 기록이 없을 때의 생성·미저장 처리는 fde-track을 따른다. 없는 WORKSTATE를 읽었다고 가정하거나 기존 기록을 초기화하지 않는다.
## 입력
확정된 요구, 현재 기능 하나, 입력 스키마, 기대 결과, 기존 실행 지시. README와 현재 코드를 먼저 읽는다.

## 절차
1. 기존 스택과 실행 방법을 유지한다. 이번 요구를 만족하는 가장 짧은 입력→처리→결과 경로를 선택한다. 비개발형 과제면 표·계산·보고서가 이 경로이며 웹앱을 만들 필요가 없다.
2. 변경 전 “구현할 행동 / 수정할 파일 / 바꾸지 않을 기준 / 확인할 사례”를 짧게 적는다.
3. 파싱·정규화, 업무 규칙, 저장, 화면을 분리한다. 같은 규칙을 여러 버튼에 복제하지 않는다. 기준 변경은 명시적인 버전이나 결정 기록과 함께 반영한다.
4. 입력 검증을 결과 형식까지 연결한다. 웹앱이면 화면 검증만 믿지 말고 서버에서도 필요한 권한·필수값·충돌을 검사한다. 인증이 필요하지 않은 로컬 과제에 임의로 회원가입 시스템을 추가하지 않는다.
5. 원문은 읽기 전용으로 다루고 결과는 새 파일에 쓴다. 기존 파일 변경은 차이를 검토하고 복구 가능한 이력을 남긴다. 운영 권한 확대, 비밀키 요구, 외부 전송, 의존성 무더기 설치를 해결책으로 삼지 않는다.
6. 사용자가 저장·승인·내보내기를 누르면 성공/실패가 구분되어야 한다. 요구된 지속성이 있다면 새로고침·재시작 후 재열람까지 검증한다. 임시 입력 저장과 확정 처리는 구분한다.
7. 변경 후 해당 사례와 인접 경계 사례를 실행한다. 실패하면 입력→판정→저장→표시 중 처음 달라지는 지점을 찾아 한 원인씩 고친다. 실패를 숨기기 위해 규칙·기대값을 바꾸지 않는다.

## 실행·빌드
터미널은 AI가 파일 처리·테스트·서버 실행을 수행하는 수단이다. 현재 프로젝트가 요구하는 명령만 사용한다. 정적 HTML에는 임의의 빌드 단계를, Python에는 불필요한 컴파일 단계를 만들지 않는다.
Browser 접속 실패는 서버 실행→포트→바인딩→경로를 확인한다. 호스팅 환경이 지정한 포트·바인딩 주소를 따른다.

## 넘길 결과
진행은 fde-track에 누적한다. implemented는 실제 구현 파일을 연결하고, 수정한 파일/정책이 영향주는 요구를 갱신한다. 기존 pass는 변경된 코드의 통과 근거가 아니다.
구현한 행동 / 변경 파일 / 실제 실행 명령과 결과 / 남은 오류 / 다음 기능.
로직 검증은 verify로, 사람의 화면 확인은 ui로 넘긴다.

# 기능별 점검표 출력 형식

프로젝트: 실제 이름 · 확인 시점: 실제 시각 · 대상 버전: 확인한 커밋/파일 · 범위: 읽은 자료와 미열람 범위

## 전체 흐름

누가 어떤 입력으로 무엇을 처리하고 어떤 결과를 받는지 한 문장으로 쓴다. 이어 실제 존재하는 단계만 화살표나 작은 Mermaid 도식으로 연결한다.

입력 출처 → 검증·규칙 적용 → 처리·저장 → 출력 → 후속 영향

읽기 전용 분석처럼 저장이 없는 흐름에서는 없는 단계를 제거한다. 구성 요소를 나열하기보다 실제 데이터가 이동하는 순서를 보여준다.

## 기능별 현황

| 기능·현재 구현 | 읽는 데이터·범위 | 처리 기준·중복·예외 | 검증 수준·근거 | 출력·후속 영향 | 남은 확인 |
|---|---|---|---|---|---|

행 작성 기준:
- 기능·현재 구현: 기능명, 구현/일부 구현/미구현, 담당 파일·함수. 원래 요구에 있던 미완료 기능도 한 행으로 남긴다.
- 읽는 데이터·범위: 실제 출처와 주요 필드·식별키, 기간·단위·대상 범위. 여러 자료 결합이면 연결 키와 관계를 포함한다.
- 처리 기준·중복·예외: 실제 적용 조건·중복 판정 기준·예외 동작을 짧게 적는다. 기준 출처와 코드 위치를 붙인다.
- 검증 수준·근거: 코드 확인/테스트 존재/실행 확인/화면 확인 중 실제 범위. 검사 입력·기대·실제·로그 위치는 핵심만 적고 상세 위치로 연결한다.
- 출력·후속 영향: 화면·응답·파일·상태와 결과가 바꾸는 집계·후속 목록·다음 행동. 영향이 불명확하면 미확인으로 표시한다.
- 남은 확인: 미구현/미검증/기준 미정/접근 불가와 구체적인 이유. 비해당에는 이유를 붙인다.

표가 너무 넓어지면 기능별 작은 카드에 같은 항목을 배치한다. 핵심 동작을 먼저 보여주되 요약에서 빠진 기능의 목록·상세 위치를 남긴다. 근거 없는 완료 개수나 통과율은 만들지 않는다.

## 결과에 영향을 주는 미확인 사항

| 사항 | 영향받는 기능·결과 | 아직 확인하지 못한 이유 | 다음 확인 동작과 근거 |
|---|---|---|---|

누락된 필수 기능, 해석 충돌, 잘못된 데이터 연결, 오래된 검증처럼 결과를 바꾸는 문제부터 정리한다. 사소한 개선 제안을 필수 누락처럼 부풀리지 않는다. 실행은 제안과 실제 수행을 구분한다.

## 중요한 결정·변경 (기록이 있고 필요한 경우)

결정 쟁점 → 확인된 결정 주체와 원문 → 반영된 코드/동작 → 영향받는 검증을 짧게 연결한다. 기록이 없는 이유는 ‘의도 미기록’, 코드에서 관찰한 효과는 ‘구현 관찰’로 표시한다. AI 제안을 사용자 결정으로 바꾸거나 과거 과정을 만들어 쓰지 않는다.

반복 점검에서는 바뀐 기능과 영향을 먼저 표시하고 이전 미완료·미검증 항목을 유지한다. 리뷰만으로 상태를 수정하지 않는다.

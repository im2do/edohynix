# 판정 범위와 예외를 고정하기

응답과 새로 작성하는 사용자 화면 문구는 기본 한국어로 쓴다. 원문 인용·고유명사·코드 식별자는 보존한다. 뜻이 같은 한자나 일본어 단어를 한국어 설명에 섞지 않는다. 사용자가 다른 언어를 요청하면 그 요청을 따른다.

FDE_HARNESS.json이 있으면 실제 package·progress·state 경로를 확인한다. 없으면 현재 키트의 scripts와 과제 폴더의 기존 기록을 사용한다. 기록이 없을 때의 생성·미저장 처리는 fde-track을 따른다. 없는 WORKSTATE를 읽었다고 가정하거나 기존 기록을 초기화하지 않는다.
여러 조건을 한 질문으로 확인했다면 답변된 조건과 미답변 조건을 따로 기록한다. 무효한 부가 기록이 기존 유효 기록을 뒤집는지, 기준 이후의 기록을 보존하는 것이 현재 유효 상태도 막는지 임의로 가정하지 말고 해당 과제 원문으로 확인한다. 규칙 변경은 progress의 의존 요구와 재검증 범위에 반영한다. 특정 과제의 수치·정답을 이 절차에 가져오지 않는다.
## 입력
질문 원문 또는 요구사항, 규정 원문과 버전, 확인된 데이터, 업무담당자 답변. 요약표는 검증한 원문의 작업용 표현으로 사용한다.

## 절차
1. 각 결과의 조건을 따로 적는다. 대상 필터 / 실제 기록 상태 / 규정상 판정 / 최종 답안 포함을 구분한다. 한 문항의 사람·기간 필터를 다른 문항으로 전파하지 않는다.
2. 규칙마다 적용 대상, 원문 조건, 한도와 단위, 등호, 예외, 근거 위치, 우선순위를 만든다. 일반 기준을 무조건 덮는 ‘업데이트 우선’ 같은 규칙도 적용 국가·기간 범위 안에서만 쓴다.
3. 제목이 비슷하다는 이유로 전체 규정을 넓게 적용하지 않는다. 금지 조건과 명시적인 허용 예외가 겹치면 문장 전체의 의미와 원문 예외를 확인한다. 단순 부분문자열 검색만으로 결론내지 않는다.
4. 해석이 갈리면 “해석 A→포함되는 범위 / 해석 B→달라지는 범위 / 갈림을 해결할 원문 또는 담당자 질문”으로 제시한다. 정답을 모르더라도 해석에 따라 바뀌는 사례부터 확인한다.
5. 임계값 바로 아래·같음·바로 위, 예외 적용·비적용, 필수값 누락을 원문 기준으로 예상 판정한다. 코드 출력에서 기대값을 가져오지 않는다.
6. 선택 메모, 관리자의 버튼, 실제 Pass 기록은 자격 충족의 증거가 아니다. 예외 승인 기능에는 승인 권한·허용 범위·사유가 확인되어야 한다.
7. 사람이 확인한 요약기준을 후속 입력으로 받으면 원문이 이번 메시지에 없다는 이유만으로 전체를 미확인 처리하지 않는다. 다만 기준 누락·충돌·해석 의존 항목은 해당 원문을 재확인하고 미확인 이유를 남긴다. 글자 제한 때문에 필수 조건을 조용히 버리지 않는다.

## 넘길 결과
규칙ID | 적용 대상 | 조건·단위·경계 | 예외 | 근거 | 기대 사례
대상ID | 실제 기록 | 규정상 적합/부적합/미확인/해당없음 | 적용 규칙 | 결과 포함 여부
조건이 확보된 범위는 build로 넘긴다. 정책 충돌은 define으로 되돌린다. 위반 없는 것과 확인하지 못한 것을 합치지 않는다.


## 업무 정책과 구현 선택을 구분
조건의 출처를 담당자·문서·권한 있는 사용자 결정·AI 가정·설계 선택으로 구분한다. 화면 편의나 개발자의 방어 코드를 업무상 금지 규정으로 승격하지 않는다. 먼저 받은 미정 답변과 뒤에 나온 제안이 충돌하면, 누가 무엇을 확정할 권한이 있는지 확인하고 양쪽 문장을 보존한다. 새 정책은 fde-track의 policy에 기록한다. 가정은 안전한 임시 동작과 확인 필요 표시로 분리하며, 임시 동작이 정답이라고 주장하지 않는다.

# 업무 요청을 판정 가능한 조건으로 바꾸기

응답과 새로 작성하는 사용자 화면 문구는 기본 한국어로 쓴다. 원문 인용·고유명사·코드 식별자는 보존한다. 뜻이 같은 한자나 일본어 단어를 한국어 설명에 섞지 않는다. 사용자가 다른 언어를 요청하면 그 요청을 따른다.

FDE_HARNESS.json이 있으면 실제 package·progress·state 경로를 확인한다. 없으면 현재 키트의 scripts와 과제 폴더의 기존 기록을 사용한다. 기록이 없을 때의 생성·미저장 처리는 fde-track을 따른다. 없는 WORKSTATE를 읽었다고 가정하거나 기존 기록을 초기화하지 않는다.
## 입력
요청 원문, 실제 자료, 업무담당자에게서 직접 받은 답변. 개발 AI가 추정한 답은 확정된 정책이 아니다.

## 절차
1. “누가 / 무엇을 받아 / 어떤 결정을 하며 / 어떤 결과를 저장·전달하는가”를 한 문장으로 적는다.
2. 현재 업무를 실제 사례 하나로 따라간다. 시작 입력, 중간 판단, 최종 사용자의 행동을 확인한다.
3. 결과를 바꾸는 모호함만 질문한다. 질문을 많이 만들지 말고 현재 기능을 막는 최대 3개를 우선한다.
   - 경계: ‘기준 적용일과 만료일이 같으면 포함되나요? 전체 기간에 유효해야 하나요?’
   - 예외·권한: ‘일반 조건과 예외가 겹치면 무엇을 적용하나요? 누가 그 예외를 승인할 수 있나요?’
   - 우선순위: ‘두 후보가 같은 기준을 만족하면 어떤 우선순위를 적용하나요, 아직 미정인가요?’
   이 문장들은 질문 형태의 예시이며 현재 문제의 규칙이 아니다.
4. 답변에서 확인된 대상·조건·예외·권한·근거를 요구사항으로 기록한다. 상태는 확정 / 제안 / 미정으로 구분한다.
5. 첫 기능의 완료 조건을 입력과 기대 결과로 정한다. 예: 입력→판정과 이유→저장→재열람. 도메인에 없는 기능은 추가하지 않는다.
6. 정책을 확인할 수 없으면 미정인 부분을 보류하고 독립적인 화면·읽기 기능을 진행한다. 임의 정책을 ‘합리적인 기본값’으로 확정하지 않는다.

## 넘길 결과
담당자 질문의 하위 쟁점별로 답변 유무를 대조하고 fde-track에 기록한다. 답하지 않은 조건은 미정이다. 후속 기능 요청이 추가되어도 최초 목표·기존 요구는 계속 남긴다.
요구ID | 사용자 작업 | 확정 조건·출처 | 미정 쟁점 | 완료를 보여줄 사례
처음에는 핵심 요구만 적는다. 각각의 문장을 코드와 테스트로 연결할 수 있어야 한다.

## 다음 단계
데이터 형식이 불명확하면 data, 적용 조건이 확보되면 rules로 이동한다. 요구를 바꿀 때는 이전 조건, 새 조건, 변경 주체와 이유를 작업 상태 파일에 남긴다.
